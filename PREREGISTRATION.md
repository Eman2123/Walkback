## Sensitivity analysis (exploratory, registered before any run)

Purpose: show how the calibrated result depends on the two unresolved-roughness and confidence assumptions. This is exploration, not validation. The default setting is not changed because of any result below.

- Tile: jezero-20m (Mars 2020 TRN HiRISE DTM, DOI 10.5066/P9REJ9JN), built with scripts/build_terrain.py using offsets row 9744, col 9700.
- Fixed inputs: habitat (50, 50), time budget 900 s, walking speed 0.5 m/s (assumed), slope cutoff 20 deg (assumed), 16 realizations with seed 1234.
- Grid: unresolved roughness in {0.1, 0.3, 0.5}, confidence threshold in {0.5, 0.7, 0.9}. All 9 combinations are reported, including the default (0.5, 0.9).
- Reported per combination: deterministic, calibrated and truth areas (km2), coverage of truth with its confidence interval, Brier score.
- Primary result: the default combination (roughness 0.5, confidence 0.9), exactly as the default run already reports it. Changing the default after seeing these results is not allowed.
- Claims rule: state the coverage of every combination. If no combination reaches 95 percent coverage, say so. Do not select a single "best" row as the result.
- Output: reports/sensitivity.csv and reports/sensitivity.md, generated by scripts/sensitivity.py.

## Post-hoc diagnostic of the default result (exploratory, logged after the result was known)

The registered default (roughness 0.5, confidence 0.9) gave an empty calibrated region and 0.0 % coverage. This section records the explanation and what was and was not changed.

- What was found: the roughness factor is also applied to the habitat cell. At the default setting the habitat cell reaches the slope cutoff in 2 of 16 realizations (12.5 %), which is more than 1 minus the confidence (10 %). In those realizations nothing is reachable, so no cell can reach the 0.9 threshold. The empty region comes from this, not from the terrain far from the habitat.
- What was NOT changed: the model used for the headline, the default setting, and reports/validation_report.md. The registered result stays a SHORTFALL.
- What was added: an optional switch (compute_run pin_start, default off) and scripts/start_cell_diagnostic.py, which writes reports/start_cell_diagnostic.md for the same 9 combinations as the sensitivity analysis. With the start cell kept passable, the default setting gives 86.9 % coverage. That is still below 95 %, and it is still reported as a shortfall.
- Status of this table: post-hoc and exploratory. It explains the headline and does not replace it. Any future model change that fixes the start-cell behaviour needs its own registration before it is run.

## Planner-slope variant (exploratory, registered 2026-11-15 BEFORE the variant was run)

Observation that motivates it (found on the committed tile, before any variant result existed): the planner DEM is 100 constant 200 m blocks drawn on the 20 m grid. Slope computed with 20 m spacing is exactly 0 inside a block and large only on block edges (every cell above 0.5 deg lies on a block edge; mean 7.7 deg on edges, 0.0 deg inside; the 20 m truth has about 4 deg in both places). So the registered planner slope is a staircase artifact, not the slope a 200 m model has.

What does not change: the registered default, the headline in reports/validation_report.md, and the API.

Variant "grid200": slope is computed on the 10 x 10 grid of 200 m block means, with 200 m spacing, and each value is repeated over its 20 m cells. Everything else is identical (speed model, cutoff, 16 realizations, seed 1234, truth slope at 20 m).

Registered analysis: the same 9 combinations as the sensitivity analysis (roughness 0.1, 0.3, 0.5 by confidence 0.5, 0.7, 0.9), habitat (50, 50), budget 900 s, speed 0.5 m/s (assumed), cutoff 20 deg (assumed). For both the registered model and grid200 report: deterministic, calibrated and truth areas, coverage with its Wilson interval, Brier score, and a secondary metric, false reach = share of calibrated cells that are not reachable in the truth. Coverage alone cannot detect a planner that is too optimistic, so it is never reported without false reach.

Claims rules: all 9 rows are reported for both models; no row is chosen as the result; if no row reaches 95 % coverage, say so. grid200 is not promoted to the default without its own registration. The scale mismatch (planner at 200 m, truth at 20 m) is the object of study, not a bug to hide.

Output: reports/planner_slope_variant.md, generated by scripts/planner_slope_variant.py.

These are consistent with a planner that cannot see steep terrain; they do not show it is safe. The next registration should name windows with steeper terrain before they are analysed.

## Steep-window validation (registered 2026-11-15 BEFORE any steep window was built or analysed)

Why: the Jezero window used so far has 0.2 % of 20 m cells at or above the 20 deg cutoff, so it cannot separate a good planner from a poor one (see the planner-slope section). This registers how steeper windows are chosen, before any of them is looked at.

Selection rule (fixed here, not tuned afterwards): scripts/find_steep_windows.py on the 1 m HiRISE Jezero DTM, with its defaults. Slope is taken on the 20 m block-mean grid (the truth grid), cutoff 20 deg, windows of 100 x 100 cells (2 km) stepped by 25 cells (500 m), no nodata, habitat cell (the window center) below the cutoff, share of cells at or above the cutoff between 2 % and 60 %, windows may not overlap, top 3 by share (mean slope breaks ties). The 60 % ceiling is there because a window where almost nothing is reachable is as uninformative as one where everything is.

Analysis on each selected window: the same 9 roughness x confidence combinations, habitat (50, 50), budget 900 s, speed 0.5 m/s (assumed), cutoff 20 deg (assumed), for both the registered model (staircase) and grid200. Report coverage with its Wilson interval, false reach, Brier score and the no-skill Brier of that window.

Claims rules: all 3 windows and all 9 rows per model are reported. No window is dropped or replaced after its result is seen; if the script returns fewer than 3 windows, report that number. If a window fails to build (nodata), say so.

Limits stated in advance: the windows are selected using the truth slope, so these results describe terrain chosen to be informative, not a random sample of Jezero or of any other terrain. The DTM is one site. Speed, cutoff and roughness remain assumptions.
